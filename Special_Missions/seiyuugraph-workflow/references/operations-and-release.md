# 数据迁移、源码版本管理与双目标发行

用于移动/清理工程、备份、Git和发布。先读项目内 `docs/OPERATIONS.md`、`docs/RELEASE.md`、`project_paths.py`；下面描述的是可复用顺序与验收，不自动授权操作真实数据、推送或上传。

## 1. 先确认路径与服务归属

历史正式工程从旧目录迁到用户文档下 `git/seiyuu_sites`，前者后来只保留兼容入口。不要把历史路径写成脚本固定默认，更不要把旧开发副本当现库。

所有运行入口共享 `project_paths.data_dir()`：默认 `.local/data`，旧根目录 `data` 仅在未迁移且确有数据时兼容；环境变量覆盖有明确边界。导出指定项目时不应悄悄读取另一工程环境变量指向的库。

读取 `.local/data/launcher.json` 与健康响应，核对随机instance、PID和实际进程目录。本机曾有IPv6其他程序和IPv4网站使用同一端口；端口号本身不能授权终止进程。停止/复用优先走项目的 `tools/service_control.py`。

## 2. 按恢复价值盘点大小

至少区分：公共源码/文档、活跃数据、API缓存、图片、旧备份、迁移归档、dist/exports、日志与测试残留。统计实际文件字节和数量，不把整个目录大小都叫数据库。

本项目的存储分工：

| 路径 | 作用 | Git/备份边界 |
| --- | --- | --- |
| `entities.sqlite3` | 角色、声优、扩展作品的权威实体库 | 旧 `entities.json` 不是当前主库 |
| `enrichment.sqlite3` / `regions.sqlite3` | 队列与地区核验 | 重启续跑所需，不只是可删缓存 |
| 根JSON | 收藏、星级/备注、关系、手工名、入库记录、图设置、后台状态 | 与实体库一起考虑一致性 |
| `images/` / `cache/` | 图片/MIME与原接口响应 | 核心备份可能不含；完整离线恢复需要 |
| `.local/` | 全部私有数据、日志、备份与本地审计 | 整体忽略 |
| `dist/` / `.runtime/` | 带数据的发行物/便携环境 | 忽略；是否保留按当前需求 |

## 3. 迁移与备份的一致性

运行中的WAL可能有主SQLite尚未包含的记录。使用SQLite backup API或一致读快照，不单独复制活跃主文件，不删除WAL“清空间”。事务的 `with connection` 不保证关闭连接，Windows上用显式close/`contextlib.closing`处理占用。

单库backup保证该库一致；多SQLite+JSON跨文件并不自动全局一致。完整应用备份通常先停止归属已核实的服务，确认写入停下，复制/backup并校验，最后恢复原有运行状态。现有完整备份入口是 `backup.bat` / `tools/backup_data.py`，会拒绝对运行中服务进行整应用备份。

验收同时看：`quick_check`、表/主键集合与内容或行数、JSON可解析与字节摘要、图片/cache逐文件数量和哈希。SQLite二进制不同不一定代表数据不同，backup或检查点会改变文件布局；反过来只有quick_check正常也不能证明记录没丢。

迁移时保留收藏、星级、备注、手工名、忽略/关注、完整度标记及任务阶段；保留未知字段，避免只导出三个实体桶丢根元数据。迁移完成后让所有启动/导出/后台工具使用同一路径，并测试空格/中文路径和重复启动。

## 4. Git提交与删归档分开判断

先确认本次明确指定的仓库、分支、remote与已有未提交改动；用户对另一个仓库的提交授权不能移用。只提交已审查的公共文件，不用强制add绕过忽略规则。

提交前的检查可包括：

```powershell
git status --short
git diff --cached --name-only
git diff --cached --check
git check-ignore .local/data/favorites.json .local/data/entities.sqlite3 .local/data/images/example.bin dist/latest.json
git ls-files
```

检查实际暂存路径与文件类型；`.gitignore`不会自动移除已追踪文件。Windows批处理/PowerShell与其他源码的换行分别处理，Git换行提示与真实空白错误分开看。

用户以“Git已有备份”为由要求删备份时，说明：Git不包含忽略数据，本地commit也不等于异地备份。列清当前数据是否另有可恢复副本、是否含图片/cache，以及本次要删什么。若删除范围明确且恢复条件已满足，按授权继续；若最后一份恢复能力的取舍仍不明确，先保留待确认。

删除前验证现存备份可读、清单与内容一致；必要时保留一份小核心快照，但明确它不是完整备份，不能借“安全”无限增加用户不需要的副本。对真实备份建立和服务重启也要在当前任务授权范围内。

## 5. 清理动作如何验收

固定清理目录白名单，对每个最终绝对路径校验位于目标项目内，拒绝越界符号链接/junction。使用单一工具处理原生路径，不跨shell拼接删除命令。

迁移后才删旧目录时，重新确认旧服务未写、目标可运行、所有原件仍匹配已验证归档；发现新增/变化文件先保留。只删可恢复或明确批准丢弃的项目，其他开发目录不因名字相似一起清掉。

清理前后核验保护对象：收藏/喜好等JSON、三份活跃库、图片、API缓存、当前dist。运行库/任务可能自然变化，需要区分合法更新与清理造成的缺失。输出删掉的实际字节、保留内容和仍可用的恢复入口。

删除归档后检索README、HANDOFF、OPERATIONS、HISTORY、旧目录提示中的归档路径；将它们改成当前状态。哈希记录证明过去校验过，不代表文件被删后仍能恢复。源码Git、核心数据ZIP、完整备份、公开静态站各有不同恢复能力。

## 6. OSS只读网站

外出查看已有信息可以烘焙静态HTML/JS/CSS + JSON + 已缓存图片，后台不搬到OSS。浏览器不调用本机 `/api`；哈希路由和相对资源路径支持子目录。

先定义公开字段白名单。现项目可导出作品/人物资料、收藏状态、评分、星标、关注、关系、地区和生日；不带UID、备注、评论、原始infobox、队列库、原API缓存或SQLite。评分/星标本身仍是偏好公开，发布给谁应与用户目标一致。

JSON/详情分块、内容哈希文件名、脚本样式版本标记；首页和配置短缓存。更新顺序是数据/图片先到、入口最后到，避免入口指向尚未上传的数据。缺图留空，不回源批量抓图。

检查文件引用、hash清单、打包ZIP的内容和隐私哨兵；用HTTP预览，直接双击文件不能可靠加载JSON。目录生成、HTTP预览和真实OSS域名/CDN上线是三层不同验证；未上传就不能报云端部署完成。

## 7. 朋友空库源码

使用源码白名单打包，包含本地图形库、启动器、必要模块、公共文档与独立测试；只创建 `.local/data/.gitkeep`，不遍历复制根目录。不要把私人历史夹具带入源码来提高通过数量。

一键入口检查现有Python/SQLite/HTTPS；缺环境时使用官方来源、固定版本和SHA校验的项目专用便携运行时，放 `.runtime`，不改全局PATH。本项目标准库服务不需要为了启动而安装pip依赖；Node仅用于开发检查。

检查中文/空格路径、端口冲突、ready后才开网页、重复启动复用、前台关闭只清自有子进程、后台退出启动窗口后仍存活、停止只作用于本目录实例。下载或校验失败时给出可重试信息，不运行未校验文件。

从真实发行ZIP独立解压运行检查，确认无隐式依赖本机安装位置/私有数据；再核对可自行导出空站。发行失败保留上次成功 `dist/latest.json`，新构建校验成功后再切换，不清掉唯一成功包。

## 8. 项目测试与交接

测试入口在创建全局store前重定向到临时数据目录，完成后清理SQLite句柄和子进程。用 `TemporaryDirectory` 与注册cleanup，避免 `tests/sql-*` 越跑越多，或生成测试JSON进入暂存区。

依赖历史个人快照的用例必须显式可选，并报告跳过数量。只有没有外部数据也能运行、且真正验证边界的测试才适合朋友源码包。

交接至少写清当前路径选择、主库和JSON职责、关系证据/完整度、操作入口、发布隐私边界、恢复限制、实际验证及未完成事项。测试总数和文件存在只描述观察时点；不要把旧阶段的测试通过当成本次变更已重跑。
