# 微信聊天记录提取语料

这是一个**综合性特殊任务**，不是单一领域的文本处理：它横跨「定位数据 → 解密数据库 → 导出目标会话 → 清洗成语料」四个环节，涉及逆向解密、SQLite 读取、数据清洗三类不同技术。按需执行，不进入日常文本处理流程。

把电脑版微信里的聊天记录，从加密数据库一路处理成可用的语料：解密 → 导出单聊 → 清洗成 A/B 对话切片，并按场景分类、给出隐私提示。全程本地运行、不联网上传数据。

## 什么时候用

- 用户想把微信某个联系人的聊天记录导出成文本/表格来分析。
- 用户要"提炼某人的说话风格"、"训练模型模仿某人的语气和应对方式"。
- 用户明确说"解析微信数据库"、"导出聊天记录成 CSV/Excel/语料"。

不适用：只要"手动复制几段话"的轻量需求；用户要的是官方备份（那是加密的 `.bak`，不是明文）。

## 核心认知（先跟用户对齐）

1. **微信官方不提供明文导出**。所有导出要么是加密备份，要么靠第三方解析本地数据库。
2. **微信 4.x 换了数据库格式**（不再是 3.x 的 `EnMicroMsg.db`）。4.x 的消息库是 `db_storage/message/message_*.db`，SQLCipher 加密，密钥需要从运行中的微信进程内存抓取。
3. **训练语料的形态不是"Excel 表格"**，而是结构化的对话配对（A 的话 → B 的话）。Excel/CSV 只是中间载体。
4. **角色映射要先定**：用户想训练"谁"——是模仿用户自己，还是模仿某个特定的人。这决定 `user`/`assistant` 怎么对应。

## 完整流程

分四步，每步有独立的完成标准：

### 1. 定位数据目录

- 先查默认位置 `C:\Users\<用户>\Documents\xwechat_files\`（4.x）和 `Documents\WeChat Files\`（3.x 旧目录）。
- 若找不到，让用户在微信里看：`设置 → 文件管理 → 文件保存位置`，这是最快定位手段。
- 4.x 数据目录下有按账号分的子目录（`wxid_xxx_xxxx`），每个账号下有 `db_storage/message/`（消息库分片）和 `db_storage/contact/`（联系人库）。

### 2. 解密

见 [references/wechat-4x-decrypt.md](references/wechat-4x-decrypt.md)。核心要点：

- 用开源工具（留痕 WeChatMsg 或 wechat-decrypt 命令行工具），**必须保持微信登录在线**才能抓密钥。
- 抓密钥过程需要**关一次微信再重开**，重开瞬间从进程内存 hook 密钥。
- 工具对 3GB+ 消息库可能报"密钥不匹配"，通常是 WAL 快照读取失败——用**绕过 WAL 的简化解密脚本**（只用 main 文件）即可，历史消息基本都在 main 里。

### 3. 导出目标会话

- 从 `contact.db` 定位目标联系人：`username`（wxid）、`remark`（备注）、`nick_name`（昵称）、`alias`（微信号）。**用户口中的称呼可能是备注名，跟昵称对不上**，要先去 contact 表里核对。
- 用导出脚本按 wxid 导出成 TXT，格式 `[时间] [说话人] 内容`。
- 导出需要 `zstandard`（zstd）依赖，缺了会直接退出。

### 4. 清洗成语料

用 [scripts/clean_corpus.py](scripts/clean_corpus.py)：

- 过滤非文字消息（Sticker/Image/Video/Audio/File/转账/系统提示等）。
- 剥离引用消息和图片 XML 噪声（`<?xml`、`aeskey`、`[引用消息]` 等）。
- 先恢复带消息头的多行记录，保留文字换行；A/B 必须不同且与输入身份一致，未知说话人、损坏消息头、倒序时间或头前未解析行会报错，不能自动归入 B。只支持已核对的双人会话。
- 默认以 30 分钟间隔切分会话，可用 `--gap-minutes` 调整；被过滤消息构成断点，不跨断点或会话合并/配对。再把连续同角色消息合并成轮，生成候选 A→B 对话对。
- 按关键词粗分类（日常闲聊 / 认真讨论 / 安慰关心玩笑），未命中的留"未分类"；分类和配对都需要抽样核对，不直接视为训练成品。
- 隐私检测只做**提示**，不自动删除——让用户判断。

## 关键决策点（需要问用户的）

1. **训练目标**：模仿用户自己，还是模仿某个特定的人？→ 决定 A/B 角色映射。
2. **分类方式**：是"忠实切片、提炼作为补充"，还是"硬性按场景切分"？默认前者（更保真、不丢信息）。
3. **隐私处理**：自动删还是提示后人工判断？默认提示、不擅自删。

## 完成标准

- 数据目录已定位，消息库已解密（验证明文可读：能列出 `Msg_*` 表）。
- 目标会话已按 wxid 导出成 TXT，行数/消息数已确认。
- 执行清洗时产出切片、场景分类和隐私提示三份文件；报告消息、过滤、续行、轮次、配对、未配对轮次和隐私提示数量。分类 JSON 保留 stats，候选配对保留会话和源消息头行号，便于抽查。已有输出不覆盖；解析错误返回非零状态，不生成本次输出。
- 全程不把解密后的明文、密钥、聊天对象身份信息外传。

## 约束与边界

- 解密工具从 GitHub 官方仓库下载，不用不明来源安装包。
- 抓密钥、解密这类操作涉及用户隐私，动手前先说明"会关微信重开""全程本地"，征得同意。
- 脚本中不硬编码具体人名/微信号，用参数传入；交付的技能文档里**不出现真实聊天对象的身份信息**。
- 临时工作目录在任务完成后按用户要求标记可删除，不擅自清理用户数据。

## 清洗脚本的使用与验证

```text
python scripts/clean_corpus.py 输入.txt --a "输入角色显示名" --b "目标角色显示名" --out 输出目录 --prefix chat --gap-minutes 30
python -B tests/test_clean_corpus.py
```

输入要求 UTF-8（允许 BOM），消息头为 `[YYYY-MM-DD HH:MM:SS] [说话人] 内容`；其后无消息头的行作为该消息的续行。若原始正文自身恰好长得像完整消息头，纯文本格式无法无歧义区分，需要先核对导出格式。A 作为 user、B 作为 assistant；模仿自己时也按输入/目标角色传参，不根据“我”字样推断。保留现有 A/B 切片格式中的角色标签，其身份以参数映射为准。

清洗仍会按现有规则剥离引用/XML、过滤非文字并规范行内空白；“保留”指清洗后的内容，不是无损原始档案。原始 TXT 应保留。时间间隔是可调整的启发式，过滤消息断点偏保守，可能减少配对；未配对轮次仍保留在切片中。未知身份等错误会提示所在行或数量，不在错误输出中打印聊天正文。

2026-10-31 使用虚构样例验证身份校验、多行保留、间隔和过滤断点、倒序/损坏输入、统计与源行、已有输出防覆盖和解析失败不产出。没有重跑微信解密、导出或真实聊天清洗；隐私检测与分类仍是有限规则提示。
