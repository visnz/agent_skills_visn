# Blender 缺失资源与无效图片引用

在工程提示文件未找到、打包资源失败，或 MaxToBlender 转换结果仍报告缺图时读取。目标是定位具体引用和实际使用范围；查询不包含自动清理、重新转换或保存工程。

## 先确认目标，再判断图片状态

沿用入口的工程身份检查。连接成功仅证明服务可用；若返回空工程或不同文件，先核对目标。用户重新打开文件后重新读取路径、版本和现场数据，不用旧连接结果解释新工程。

先核对报错对应的资源类型与完整路径，不把图片、外部链接库和缓存文件混为一类。搜索名称或路径中的关键词只是发现候选，不能成为删除条件。

对于图片，结合以下状态判断：

- 记录 `source`、`filepath`、`library`、`packed_file` / `packed_files`、`has_data`、`size`、`users` 与 `use_fake_user`。
- FILE 图片已打包时，外部路径不存在不等于图片丢失；有必要时检查内嵌数据能否读取。有效但尚未载入的图片也可能 `has_data=False`，不能单独据此判断损坏。
- FILE 图片未打包、路径无效且无可用图片数据时，才将它列为缺失引用。GENERATED 图像、UDIM、序列和视频按各自来源检查，不把普通文件存在性判断套用于所有类型。
- 用 `bpy.path.abspath(path, library=image.library)` 处理 Blender 的 `//` 路径及链接库基准。裸名称或普通相对路径可能依赖运行目录；同时保留原始路径、解析基准和错误文本，不把某次显示的 `C:\Checker` 写成固定配置。

## 沿引用链定位影响范围

先查询 `bpy.data.user_map(subset={image})`，找出直接引用图片的 ID。再检查相应材质、世界、节点组等节点树中的图片节点及输出连线，记录通向哪个节点和输入。节点连接只证明它进入这条链，是否影响当前画面还要检查有效输出和消费者。

图片的 `users` 大于零不能证明它影响可见物体。继续对引用它的材质或节点组查询使用者，核对对象材质槽、嵌套节点、几何节点的材质输入等实际依赖。只扫描对象材质槽没有命中，不能直接宣称材质未使用。

`use_fake_user=True` 会让数据块在没有实际使用者时继续保存；材质因伪用户留下，也会连带保留它引用的图片。区分：

- 实际用于场景输出的资源；
- 仅由保留的材质或节点组引用的资源；
- 没有真实使用者、仅因伪用户保留的数据块。

后两类也可能是用户有意保存的备用材质或资产，不能仅凭未使用自动删除。

## MaxToBlender 的 Checker 特例

既有转换记录中，FBX 的 Checker 纹理项缺少 `FileName` / `RelativeFilename`，导入器回退到纹理名称，形成没有图片文件的 FILE 引用。这种错误不需要新建同名目录，也不靠改名恢复程序棋盘格。

已记录的队列工具 v0.3.2 改为逐图打包：遇到缺图保留引用并给出警告，让已有模型继续保存。因此“转换已成功”与“后续打包仍提示 Checker 缺失”可以同时成立；此改动没有生成替代贴图或清理引用。

只有当前工程的图片状态与引用链符合时，才采用这一解释。未读取当前来源的 FBX / Max 文件时，应说明与已知案例一致，而非宣称本轮重新验证了导出端原因。名字相同但图片有效时，不套用此特例。

## 处理与验证

用户只要求诊断时，交付问题图片、引用节点、实际使用者和检查范围，保持只读。

用户要求修复后，按实际用途选择：保留仍需使用的资源并寻找原文件；为丢失的程序贴图重建所需效果；或清理确认不需保留的无效引用。只处理已确认的目标，不批量清理所有 Checker、所有伪用户材质或全部孤立数据。

清理或替换前记录链接和相关输入值。若仍用于着色，不能随意用某个固定数值代替原贴图；如果修改 linked 数据或资产定义，先明确影响范围。需要持久化时按用户授权保存。

修复后重新检查目标图片、引用链及实际材质效果。仅在已执行相应验证时，才声称打包或保存不再报错；失败的 `pack_all()` 也可能已经打包了部分资源，不把它当作无副作用的诊断探针。

## 脱敏案例：伪用户材质保留 Checker

2026-11-13，在 Blender 5.3.0 做了只读工程检查。首次连接返回空工程；用户重新打开目标后，重新读取文件身份，再继续诊断。

当前工程中的 `Checker` 为 FILE 图片，路径是裸名称，未打包、无像素数据、尺寸为 `[0, 0]`。直接使用者为一个导入材质，图片节点的 Color 连到 Principled BSDF 的 Specular IOR Level。继续查询材质的 `user_map`，真实使用者为空，但 `use_fake_user=True`，解释了无场景使用者的材质为何仍保留这张坏引用。

当时对未打包 FILE 图片的普通路径检查只发现这一项缺失；不据此宣称所有外部库、UDIM、视频或缓存均完整。证据来自当次 Blender 只读查询，没有保存原始模型、截图、完整会话或可识别的工程路径与材质编号。

已验证到诊断与引用追踪。本轮没有删除材质或图片，没有重新执行打包、保存或重跑 Max 导出；清理能消除提示是待授权验证的处理方案，不能写成已修复案例。原 FBX 导出端机制来自既有转换记录，本轮仅确认当前残留引用与其相符。
