# 多人协作插件仓库：模块归属与分支留档

只在开发涉及协作规则的 Blender 插件仓库时读取。普通单人脚本或一次性场景操作不需要这份流程。

以下五要素、模块归属、分支基点和留档细节来自 pond_bekkan 的一次实践。仅当当前项目采用相同协议时执行；先以当前项目规则和本次用户授权判断，不自动新增审批、stash、合并或日志要求。独立新增也须符合当前规则，不能因历史案例允许就自行豁免。

## 识别协作规则

开工前检查仓库根目录是否有 CLAUDE.md（Claude Code 读取的项目指令）、AGENTS.md 或类似命名的文件。真实案例（pond_bekkan）里的结构：

- 代码按模块（通常是一批具体文件路径）划归三类：专属 A、专属 B、共同维护（Mixed）。
- 共同维护模块通常是因为两方代码合并进了同一个文件，或被重写为共同资产（如注册中心、唯一的 Preferences 类、模式分发逻辑）。
- 文件里会明确写"改对方专属或共同模块前必须做什么"，以及是否要求每次开发留一份开发日志。

识别当前实际适用的规则，结合本次用户明确要求和已有授权执行。下文保留案例规则的细节，不代表所有插件仓库一律采用。

## 改动前的边界判断

当时项目区分“纯新增”和“修改既有逻辑”，以下是其具体做法；额外同意仅在当前规则确实要求且尚未获授权时请求：

- **纯新增**：新增一个独立的函数/类/operator，不修改文件内任何已有函数、类的实现，也不改变它们的注册方式。即使新增内容所在的文件被标记为"共同维护"，只要没碰已有代码，风险就相对可控——但仍然要在交付说明里讲清楚：改了哪个文件、新增了什么、这个文件原来是谁的、为什么新增的内容不影响已有逻辑。
- **修改既有逻辑**：只要触碰了对方专属模块或共同维护模块里已经存在的函数/类/行为，不管改动量大小，都要在动手前向用户说明五要素：
  1. 要改哪个文件/函数；
  2. 这个模块原来的归属（谁负责/哪一方的代码/是否双方共用）；
  3. 修改理由；
  4. 是否会影响另一方依赖这份代码的 UI 或行为；
  5. 是否需要同步更新仓库里记录模块归属的文档（如果项目要求维护这类文档）。

获得明确同意后才改。"看起来很小的改动"不构成跳过这一步的理由——真实案例中，给已有的、大家都在用的 `_switch_sidebar_category()` 辅助函数新增一个调用方，以及给注册流程追加一条快捷键绑定，都先完整走了这五点说明，即使改动本身只有几行。

### 复用已有的辅助函数而不是重新实现

新功能需要的能力如果已经在仓库里存在类似实现（哪怕是给另一个用途写的），优先复用或抽出共享逻辑，而不是重新写一遍。真实案例中：

- "棋盘格陈列"新功能需要算物体世界空间包围盒，而仓库里已有一个"整理"模块的函数用几乎同样的思路算了"原点设到底部"，于是直接参考那段代码的写法（角点变换、游标挪动、`origin_set`、状态还原），只是按新功能的需求调整了取值方式。
- "锚点到顶/底部中心"同样复用了这个"挪游标 + `origin_set(ORIGIN_CURSOR)` + 还原选中与游标状态"的固定套路，而不是用别的方式（比如直接改 `location` 再手动算 `matrix_world`）去达到同样效果。

这样做的好处是行为与仓库已有功能的既定模式一致，减少了评审者（人类维护者）需要理解的新模式数量。

## 分支策略

### 一个功能一条分支

当时项目约定每个独立的新功能或修复从公共开发分支（比如 `bekkanDEV` 这类团队协作分支，不是 `main`）切出自己的分支。判断"独立"的标准是：这个改动和另一个正在做的改动在语义上无关，即使两者都恰好要改同一个文件。

真实案例里当前分支曾有 WIP，同时要开始新功能。下面保留当时的隔离步骤，仅作历史记录；不直接套用，尤其不能默认 stash 用户改动。先选择不扰动已有改动的方案，确需移动时说明具体范围和恢复方式：

1. 先确认当前分支工作区状态（`git status`），看是否有未提交的改动。
2. 如果有未提交的改动且与新任务无关，`git stash -u` 挪走。
3. 切换到正确的基点分支（公共开发分支），从这里切出新分支。
4. `git stash pop` 恢复之前的改动——如果这些改动本应该属于一条独立分支而不是当前分支，还需要再切一次。

反面教训：如果不小心把两件不相关的事提交在同一条分支上，后续合并时会让 reviewer 难以单独撤销其中一个改动；发现堆错了要主动拆开，而不是将错就错继续往上叠。

### 合并顺序与冲突处理

多条独立分支如果都从同一个基点切出，并且都往同一个文件的"尾部同一区域"追加内容（常见于：operator 注册用的元组/列表、面板 `draw()` 方法里顺序追加的按钮、项目里记录模块归属的表格文件），合并第二条及以后的分支时会产生冲突。这是结构性的、可预期的现象，不代表操作有误。

处理方法：

1. 逐个合并，而不是一次性合并所有分支（更容易定位冲突来源）。
2. 冲突出现时，读冲突块两侧的完整内容，确认哪些是"这条分支新增的"、哪些是"上一条分支已经合并进来的"。
3. 当双方是独立新增时可以“两边都保留”，但应检查注册和行为兼容；不是所有冲突都这样解决——删掉冲突标记，把双方新增的内容依次排列在一起，不要选一边删掉另一边（除非确实是同一处逻辑的真冲突，而不是两边各自新增独立内容撞在一起）。
4. 每个文件解决完冲突后，先全文检索一遍确认没有残留的 `<<<<<<<` / `=======` / `>>>>>>>` 标记，再做静态语法检查。
5. 合并完成后，在真实环境里重新加载一次插件/代码，确认所有分支的功能都注册成功、互不冲突（不要只信赖"合并没有报 ERROR"）。

### 合并前补测

如果某条分支上次只做过受限环境下的验证（比如只用背景脚本模拟过，没有真实交互验证），在合并进公共分支前先补一次更接近真实使用场景的测试，并把测试结果追加写进该功能当时的开发日志里，再合并。不要把"之前记录为未完成的验证"直接带着合并，除非已经明确告知用户这点风险并获得同意。

## 留档

如果项目要求"每次开发留档"，按它指定的目录和命名规则（常见做法是按日期和主题命名的独立文件，放在约定的文档目录下）创建或追加记录，内容至少包含：

- 本次目标与范围（用户提出的具体需求是什么）；
- 跨边界说明（如果触发了上面的"改动前边界判断"，把五要素的说明原样记录进去）；
- 具体改了哪些文件/函数；
- 调试与试错过程（包括走过的弯路、发现问题后怎么改的，不要只写最终版本，中间的返工本身就是有价值的记录）；
- 测试结果（哪些验证过、用什么方式验证的、哪些受限于环境没验证）；
- 未完成的 TODO 和已知限制。

记录格式延续该项目已有的留档文件的写法（标题层级、小节命名），不要自创一套新格式与现有文档风格不一致。
