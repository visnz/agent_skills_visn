# 用真实连接的 Blender 验证 operator，同时保护用户现场

只在需要对插件代码做端到端验证（而非纯语法检查）时读取。

## 为什么优先用真实连接而不是只用背景脚本

`blender --background --python` 跑的探针脚本能验证核心逻辑不崩溃、数据计算正确，但它通常需要用 `context.temp_override` 或直接调用 operator 的 `execute()` 方法来绕过真实的选中状态、3D 视口上下文——这恰好绕开了很多真实 bug 的触发条件（比如 operator 的 `poll()` 依赖的上下文、`invoke()` 里依赖的事件/窗口状态）。

有真实连接（如 MCP）能操作用户正在使用的 Blender 时，优先走真实的 `选中物体 → 设为 active → 调用 operator（不传参数绕过，走正常的 bpy.ops 调用）→ 检查结果` 流程。这样测出的问题才是用户真实点按钮会遇到的问题。

真实案例：一个"单体迁移动画到上级"的修复，最初只做过背景脚本测试（用 `temp_override` 模拟单选）就被标记为完成候选；重新用真实连接按正常选中流程跑一遍后，才确认 Noise 修饰器参数、frame 1/20 的世界坐标在真实 GUI 流程下也完全一致——这一步不能被背景脚本测试替代，因为背景测试本来就是为了绕开真实上下文而设计的。

## 操作前确认现场

**不要假设连接到的是空场景或测试场景。** 先用场景信息查询工具读一次当前场景，确认物体数量级、是否有骨骼绑定等复杂结构。如果数量级明显不是"几个测试物体"，就是用户正在使用的真实工程，后续所有操作都要避免影响已有内容。

### 测试数据的建立与清理

1. 建一个命名清晰、容易识别的临时集合（比如带 `TMP_` 前缀的名字）。
2. 所有测试用的物体、网格/曲线数据块都链接到这个集合里，不要散落在场景根集合。
3. 测试结束后，按名字精确删除这个集合及其包含的数据块（物体 remove 之后，检查对应的 mesh/curve 数据块 `users == 0` 再一并清理，避免残留孤立数据）。
4. 清理后用一次列表查询确认没有残留以约定前缀命名的物体，也没有残留测试集合。
5. 全程不要对场景执行 `select_all` + 批量操作之类可能波及用户已有物体的指令，除非已经先精确缩小到了测试集合范围内。

### 不要替用户切换模式

如果发现当前连接到的 Blender 处于编辑模式（或其他非 Object Mode），不要为了跑测试强行切回 Object Mode——这会打断用户手头正在做的事。遇到这种情况：

- 先确认这是外部环境状态（用户当时在做别的操作），不是代码本身的 bug 导致的。
- 退一步做能在当前模式下验证的部分（比如纯计算逻辑可以脱离 `bpy.ops` 调用单独验证）。
- 把"受限于用户当前模式，未覆盖的端到端分支"明确记录为未验证内容，不要在交付说明里含糊过去，也不要事后假装测过。
- 等用户确认已经退出该模式，再补测剩下的分支。

## Context 相关的常见报错

`bpy.ops.object.select_all` 等很多 operator 的 `poll()` 依赖 `context.mode == 'OBJECT'` 以及存在有效的 3D 视口区域。通过某些外部脚本执行通道调用时，`bpy.context` 可能缺这些（比如 `bpy.context.area` 是 `None`），表现为：

```
RuntimeError: Operator bpy.ops.object.select_all.poll() failed, context is incorrect
```

这不等于被测的 operator 代码有 bug。排查顺序：

1. 先查 `bpy.context.mode`，确认不是用户正处于非 Object Mode（这种情况见上一节，不要强切）。
2. 如果 mode 正确但仍报错，找到一个真实的 `VIEW_3D` 区域和它的 `WINDOW` region，用 `context.temp_override(window=..., screen=..., area=..., region=...)` 包住整段"选中 + 设置 active + 调用 operator"的代码，而不是只包住最后一步调用——拆开执行容易在中间步骤又丢失正确的 override 上下文。
3. 同一个 window 的 `screen` 下可能有多个 `VIEW_3D` 区域（比如分屏布局），取第一个能用即可，不需要特别挑选。

## 连接抖动

执行过程中偶尔会遇到类似"连接已被远程主机关闭""通信错误"的瞬时报错，尤其是在创建数据块、修改较多状态的连续调用之间。遇到这种情况：

1. 先重新查一次连接/服务状态，确认是否已经自动恢复。
2. 恢复后，重新查询刚才操作的对象是否真的创建/修改成功——有时报错发生在调用返回之前，之前的改动并没有真正生效（比如某次创建数据块的调用因为连接断开实际没有执行，之后的代码以为它存在会报 `KeyError`/`None`）。
3. 确认实际状态后，用小步骤重新执行缺失的部分，不要假设"上次的报错只是网络问题，数据一定已经改好了"。

把每一步操作拆得足够小（比如创建数据块、设置属性分开成几次调用），能让这类抖动造成的影响更容易定位到具体哪一步没有真正生效。
