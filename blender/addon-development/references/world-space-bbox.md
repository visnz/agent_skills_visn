# 旋转/缩放物体的世界空间包围盒：局部 bbox 整体变换会偏大

只在需要计算物体当前实际旋转/缩放表现下的几何边界时读取（比如"把原点移到物体顶部/底部中心""按物体实际大小做网格排布"一类需求）。普通的、物体没有被旋转的场景不会暴露这个问题。

## 问题

`obj.bound_box` 返回的是物体**局部空间**下的轴对齐包围盒（AABB）的 8 个角点。这个局部 AABB 本身就可能比物体真实几何形状更宽松——比如一个圆柱体，它的局部 AABB 是一个方盒，方盒的四个角是圆柱体表面完全没有覆盖到的空白区域。

物体没有旋转（旋转为单位旋转）时，把这 8 个局部角点整体变换到世界空间（`[obj.matrix_world @ Vector(c) for c in obj.bound_box]`），恰好仍然是这个物体最终呈现形状的真实世界空间边界——因为平移和缩放不会让"方盒套圆柱"的间隙变得有意义。

**物体一旦被旋转**，问题就出现了：这个本来就比真实形状更宽松的局部 AABB，被当作一个整体转了个角度。转过去之后再对这 8 个点求 min/max，得到的范围只会比真实几何转过去之后的范围更大——相当于"盒子套盒子"再整体旋转，外层盒子转出来的范围必然包住内层也必然更宽。

实测数据（pond_bekkan 真实案例）：一个圆柱体，位置 `(10,10,1.5)`，旋转 `(0.7, 0.4, 0.3)` 弧度，缩放 `(1, 2, 0.5)`：

| 方法 | 世界空间 Z 最大值 | 世界空间 Z 最小值 |
| --- | ---: | ---: |
| 局部 bbox 8 角点整体乘 `matrix_world` | 3.6045 | -0.6045 |
| 真实顶点逐个变换到世界空间后求 min/max | 3.2738 | -0.2738 |

两者相差 0.33 个单位——这正是用户反馈"结果比视觉上的边界更宽"的量化来源。

## 正确做法

不要对局部 bbox 整体做变换，而是取物体的**真实几何控制点**，逐个（不是整体）变换到世界空间后再求 min/max：

- **Mesh**：遍历 `obj.data.vertices`，每个顶点单独 `obj.matrix_world @ v.co`。
- **Curve（贝塞尔样条）**：遍历 `obj.data.splines`，对 `BEZIER` 类型的样条，每个控制点要同时算上端点 `bp.co` 以及两条手柄 `bp.handle_left` / `bp.handle_right`，三个点都单独变换到世界空间。贝塞尔曲线段必然落在"两端点+两手柄"这四个控制点的凸包内，只看端点会漏算手柄把曲线拉出去的那部分范围。实测验证：一条两点贝塞尔曲线，端点 Z 范围是 `[0, 3]`，但其中一个手柄把 Z 拉到了 `-2`、另一个手柄拉到了 `5`，正确算法得到的世界 Z 范围是 `[-2, 5]`，只看端点会漏掉 `[-2, 0)` 和 `(3, 5]` 这两段。
- **Curve（非贝塞尔，NURBS/POLY）**：遍历 `spline.points`，坐标是 4 分量（含权重），取前 3 维再变换。这部分在真实案例中没有做完整的端到端 operator 验证，只是实现上沿用同样的"取控制点而非 bbox"的思路；如果控制点本身就落在最终曲线的凸包内（NURBS 通常如此），结果方向上是安全的（不会比视觉更宽），但建议在用到这个分支时针对真实 NURBS 曲线补一次验证。

对取到的所有世界空间点求 `min`/`max`：中心点（比如 XY 方向上要找的中心）应该取 `(min + max) / 2`（包围盒中心），而不是所有点坐标的算术平均值——算术平均值会被顶点密度不均匀带偏（比如物体一端的顶点特别密集，平均值就会被拽向那一端，偏离真正的几何中心）。

## 验证方法

判断一个"计算世界空间边界"的实现是否正确，用一个经过**非单位旋转 + 非均匀缩放**的测试物体做对照：

1. 分别用"局部 bbox 整体变换"和"真实几何点逐个变换"两种方法各算一次结果。
2. 如果物体没有旋转，两者应该完全相同（这时测不出问题，所以验证测试物体必须有旋转）。
3. 如果物体有旋转且不是完全对称的形状（圆柱、不规则 mesh 都适合），两种方法的结果应该有明显差异，新方法的范围应该更贴近真实几何、比旧方法更"紧"。
4. 跑一次真实的 operator 调用（比如把原点真的移到算出的目标点），再独立读一次物体变换后的真实几何点坐标，确认 operator 产生的结果和"真实几何点"算出来的理论值完全一致，而不只是"看起来差不多"。
