# 技能建设规范

## 目的与适用范围

用于本仓库的任务复盘、技能新增和更新。目标是积累能改善后续执行的经验，保持技能容易发现、按需读取、如实描述能力。每次任务都可以复盘，文件只在有明确价值时变更。

用户的明确需求决定本次范围。整理经验不自动授权提交、推送、发布、安装技能、操作真实业务数据或修改外部配置。

## 沉淀前的五个问题

| 判断问题 | 需要明确的信息 | 如何影响整理结果 |
| --- | --- | --- |
| 下次遇到什么情况，这条经验会改变做法？ | 触发场景、用户目标和实际收益 | 无明确复用用途时，可保留为案例或无需修改 |
| 它在什么范围内成立？ | 必要的工具、版本、环境和任务条件 | 限定规则范围，避免把特定工具行为泛化 |
| 哪些经过观察或验证，哪些仍是推测？ | 事实、结论、不确定性与依据 | 证据不足的原因判断不写成确定的操作要求 |
| 已有技能能否容纳？ | 与现有技能的触发场景、流程和结果的关系 | 优先更新；确有独立能力边界时再新建 |
| 怎样判断这条经验仍然有效？ | 可观察结果、验证方式与失效迹象 | 确定本次检查和后续实践中需要关注的内容 |

这些问题用于作出决定，不要求每次逐项填表。小修正可简短说明；复杂或容易出错的流程再展开记录。不要为满足形式编造收益、原因或验证结果。

## 选择复盘结果

一次任务可同时产生多种结果，也可以无需修改。

| 结果 | 适用条件 | 放置方式 |
| --- | --- | --- |
| 更新已有技能 | 改善已有任务的判断、操作或完成标准 | 修改相关 SKILL.md 或其资源 |
| 补充参考资料 | 有复用价值，但只在特定操作中需要 | 放入 references/，从入口或相关资料说明何时读取 |
| 增加或修正脚本 | 重复逻辑值得固化，或确定性执行能显著降低出错概率 | 放入 scripts/，说明参数、依赖与使用条件，并实际验证 |
| 保存案例或待验证记录 | 现场有参考价值，但还不足以形成稳定规则 | 按需放入相关技能的 references/，标明历史现场和未确认事项 |
| 新建技能 | 有独立且清晰的触发场景与结果，现有技能难以合理容纳 | 按领域建立技能文件夹，更新 README 索引 |
| 无需修改 | 没有新的复用信息，或已有内容已经覆盖 | 在交付中简要说明，无需新增文件 |

案例应服务未来判断。只记录与复用或验证有关的信息，不默认保存整个对话或为每次微调创建复盘文件。尚无合理归属的零散观察可以留在当次对话，不急于建立新的知识目录。

## 内容分层

- **SKILL.md**：清晰、可区分的触发描述，核心决策、必要约束、完成标准和按需资料入口。只写会改变 Agent 决策或执行的信息。
- **references/**：条件性流程、技术细节、案例和必要的验证依据。资料应有读取入口，不要求所有任务加载全部参考文件。
- **scripts/**：需要复用的可执行操作。路径、端口和身份等现场信息通过参数或现场发现获取；依赖与副作用应明确。
- **assets/**：确实用于生成结果的模板或素材，有需求时再添加。
- **README.md**：项目介绍、技能索引、使用说明与建设原则。
- **AGENTS.md**：仓库维护要求和规范入口，不重复详细方法。

延续现有目录和分类，不因一次整理擅自重组仓库。新技能具备带 name、description 的 YAML frontmatter；名字和描述应帮助准确选择技能，避免用宽泛描述吸引无关任务。

## 从案例提炼规则

先记录观察到的现象和已验证的动作，再决定可以概括到什么范围。“做了 A 后成功”不等于“失败一定由 B 导致”。推测应明确标记，不把未经确认的归因写成固定修复步骤。

优先写选择条件和结果要求；只有真实约束或脆弱操作才规定固定步骤。不要因为一次失败不断叠加普遍适用的“必须”。用户的一次性要求不自动成为长期偏好。

例如 Blender 入库任务：

- 按实际工程路径确认跨工程操作目标：可作为相关技能的判断规则。
- 预览如何嵌入并验证保存：进入资产入库参考流程。
- 本次使用的端口和参数：留在案例，执行前重新发现或确认。
- 调用失败但原因未确认：记录现象、已验证替代方式与适用条件，不宣称已经找到根因。

案例及交付文档避免写入密钥、私人聊天内容和无必要的身份信息；示例优先使用占位符。必要的现场路径须注明历史性质，不作为默认配置。

## 验证与后续迭代

### 本次变更检查

按变更影响选择必要检查：

- 描述的触发范围与实际能力一致，完成标准能够观察或检查。
- 引用存在且有明确读取时机；README 索引与本次新增、改名或能力变化一致。
- 脚本参数、依赖与文档一致；新增或修改的脚本验证相关行为及必要失败条件。
- 新建或明显修改技能入口时，使用当前环境可用的技能校验工具检查结构；工具不可用时做相应人工检查并如实说明。
- 检查最终差异，避免覆盖无关内容或用户已有改动。

结构校验通过不代表执行能力已经验证。文档小改动通常检查链接、内容和差异即可；不要为了形式运行无关业务操作，或编写仅匹配标题、措辞的测试。

### 真实行为验证

明确区分：文档或脚本检查通过、本次任务中已验证、后续同类任务中再次验证。只声明实际达到的范围；第一次经验可以先保存，不必虚构跨场景验证。

后续实践关注 Agent 是否正确选用技能、按需读取资料、保留用户意图，并完成到可检查结果。复杂或高风险流程可在授权范围内安排代表性试用；涉及真实数据、外部服务或额外副作用时遵守本次授权范围。

发现反例时先核对环境和原规则的条件，再修改、收窄或删除失效内容。修订依赖旧结论的引用，避免在旧规则旁不断堆叠冲突的补丁；不强制维护额外状态表或变更日志。

## 完成交付

按实际规模简要说明：

1. 沉淀了什么，为什么值得复用；若无需修改，说明理由。
2. 放到了哪里，为什么更新、新建或保留为案例。
3. 验证了什么，尚有哪些适用条件或未验证部分。
4. 哪些经验暂未进入技能，以及原因；没有时无需展开。

这些说明通常放在当次对话。只有影响未来执行或维护的依据才保存到仓库，不机械复制交付内容。Git 提交、推送等状态按事实说明。

## 工作量与成本评估

任务开始前判断规模：小规模且边界明确的工作可直接继续；预计涉及大量文件、全量资料读取、多次长链试错、昂贵工具或长时间运行时，先向用户说明预计范围、主要成本来源、验证方式及分阶段/缩小方案，等待用户选择。用定性估计和可观察数量说明，不编造精确 token 数或费用。先做低成本抽样有助于估计，但不先运行高成本部分再补报告。

执行中范围或重试成本明显增加时再次评估，暂停扩展性工作和无新依据的重复尝试，反馈已完成、剩余不确定性与下一步选择。用户对某一范围的授权不意味着接受无限试错；已明确选择的范围内继续执行，不重复索取同一决定。

## 在较大任务收尾时提示沉淀

当一项较完整、较大的任务结束或接近结束，并出现会改善后续执行的新经验时，说明一两条候选经验，询问是否按 README 与本规范整理。不要求固定任务时长或 token 阈值；以交付是否形成完整阶段、经验是否值得复用判断。小修小改、普通问答和同一任务中间步骤不提示。每项任务提示一次，已要求整理则直接执行，拒绝后不重复询问。不为提醒而强行发明经验，也不自动修改技能库。

## Special_Missions 的适用例外

特殊任务允许保留窄范围流程、特殊工具行为、任务专用参数和案例经验。它们能帮助再次完成相似特殊任务，就有保存价值；不要求每项内容具备跨领域通用性，也不因特殊性强就强制拆分。明确哪些参数是该方案的条件、哪些只是当时现场。

这放宽的是复用范围和内容形态，不放宽事实与推测区分、脚本正确性、说明一致性、授权、隐私和验证真实性。任务不一定完整重跑过时，如实记录验证到的阶段即可。

## 同一项目的新功能如何归档

同一个长期维护项目里的新功能，默认先归入已有项目技能的按需流程。后续可重复操作的方法与脚本继续维护；一次开发的取舍、环境和验证另存案例，不能把可执行能力只留成历史故事。

只有工作对象、触发场景、交付物或授权边界明显独立，且单独入口能改善发现与装载时，才新建 Skill；领域相同不强求合并，功能新增也不自动拆分。合并时更新入口描述和分流，不把所有细节追加进主文；保留有价值的流程、脚本、案例及验证依据。

迁移前检查现有引用、旧命令和安装关联；按需求保留轻量兼容路径，避免两个完整实现同时维护。仓库外安装不自动改动，交付时说明仍需处理的关联。README 目录树只展示领域/技能入口，不枚举全部案例文件；具体按需入口由各技能维护。
